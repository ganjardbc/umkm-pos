## RBAC / Client-Side Permission

- **Lokasi**: `apps/web/src/modules/transaction/services/rbac.ts:1-2`
- **Kategori**: rbac-misconfig
- **Severity**: LOW
- **Deskripsi**: `PRINT` didefinisikan sama persis dengan `READ` (`'transaction.read'`). Tidak ada permission code terpisah untuk cetak struk, jadi role apapun yang bisa read transaksi otomatis bisa print — tidak bisa dipisah granularity-nya.
- **Rekomendasi singkat**: kalau print memang harus dipisah dari read, buat code `transaction.print` sendiri; kalau memang disengaja sama, tidak perlu alias var terpisah.

- **Lokasi**: `apps/web/src/modules/transaction/pages/index.vue:135-151`
- **Kategori**: guard-disabled (client-side only)
- **Severity**: LOW
- **Deskripsi**: Tombol aksi (print/cancel/advance-status) hanya di-`disable` berdasar `isHasPermission()` di client. Ini standar pattern di project (defense di UI), tapi kalau endpoint backend (`postCancelTransaction`, `patchTransactionStatus`) tidak menegakkan permission yang sama server-side, user bisa panggil API langsung dan bypass.
- **Rekomendasi singkat**: verifikasi `PermissionGuard` + `@RequirePermission()` benar-benar dipasang di endpoint `POST /transactions/:id/cancel` dan `PATCH /transactions/:id/status` di apps/api (di luar scope scan ini, karena ini folder frontend saja).

## Tenant / Outlet Scope Reliance on Client Input

- **Lokasi**: `apps/web/src/modules/transaction/components/Cart.vue:424-437` (payload `postTransaction`), `apps/web/src/modules/transaction/pages/index.vue:243-249` (payload `getListTransaction`)
- **Kategori**: cross-tenant-scope (client-input pattern — riwayat HOTFIX-RBAC-CROSS-TENANT)
- **Severity**: HIGH (butuh verifikasi backend)
- **Deskripsi**: `outlet_id` diambil dari `getOutlet()` (localStorage `APP_ACTIVE_OUTLET`, client-controlled) dan dikirim sebagai field body/query ke `POST /api/v1/transactions` dan `GET /api/v1/transactions`. Sesuai CLAUDE.md project, setiap query backend WAJIB scope dari `merchant_id`/outlet dari JWT, bukan dari client. Kalau endpoint backend memakai `outlet_id` dari body/query apa adanya tanpa cross-check terhadap outlet yang di-assign ke user di JWT, user bisa modifikasi request (devtools/Postman) untuk baca atau membuat transaksi di outlet lain dalam merchant yang sama, atau merchant lain kalau outlet_id tidak divalidasi kepemilikan merchant-nya.
- **Rekomendasi singkat**: audit endpoint `apps/api` terkait (`transactions.controller`/`service`) — pastikan `outlet_id` dari client divalidasi terhadap outlet yang di-assign ke user (dari JWT), bukan dipercaya langsung. Ini di luar scope folder yang di-scan (frontend only) — sarankan audit-scan terpisah untuk `apps/api/src/modules/transaction` atau modul terkait untuk konfirmasi.

## Client-Trusted Monetary Fields

- **Lokasi**: `apps/web/src/modules/transaction/components/Cart.vue:430-432`, `apps/web/src/modules/transaction/pages/index.vue:321-324`
- **Kategori**: client-trusted-input
- **Severity**: MEDIUM (butuh verifikasi backend)
- **Deskripsi**: `cash_received` dan `change_amount` dihitung di client lalu dikirim sebagai field ke `postTransaction`/`patchTransactionStatus`. Item payload sendiri hanya berisi `product_id` + `qty` (harga tidak dikirim client — good, harga kemungkinan besar diambil ulang dari katalog di backend). Tapi kalau backend menyimpan `cash_received`/`change_amount` apa adanya tanpa recompute dari `total_amount` server-side, nilai struk (cash paid/change) bisa dimanipulasi user meski tidak mempengaruhi total transaksi.
- **Rekomendasi singkat**: pastikan backend recompute/validate `change_amount = cash_received - total_amount` (server-side total), bukan trust dari client, terutama karena field ini muncul di struk cetak (ReceiptModal/bluetoothPrinter) sebagai bukti transaksi.
