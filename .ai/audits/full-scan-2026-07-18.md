## RBAC module (`apps/api/src/rbac`)

### 1. Cross-tenant leak via getUserRoles + guard dimatikan
- **Lokasi**: `apps/api/src/rbac/rbac.controller.ts:206` + `apps/api/src/rbac/rbac.service.ts:266-285`
- **Kategori**: cross-tenant-scope + guard-disabled
- **Severity**: CRITICAL
- **Deskripsi**: `GET /rbac/users/:userId/roles` punya `@RequirePermission('role.read')` di-comment (baris 206), dan `RbacService.getUserRoles(userId)` query `prisma.user_roles.findMany({ where: { user_id: userId } })` tanpa filter `merchant_id`/outlet sama sekali. User terautentikasi dari merchant manapun bisa pass `userId` arbitrary dan baca nama, email, status, role, permission list, outlet id/name/slug milik user di tenant lain. Recurrence langsung dari pola HOTFIX-RBAC-CROSS-TENANT, di modul RBAC sendiri.
- **Rekomendasi singkat**: Nyalakan lagi `@RequirePermission('role.read')`, scope query ke user yang `merchant_id`-nya cocok dengan caller (join lewat `users` atau filter `outlet_id` by outlet milik merchant caller), 404 kalau tidak cocok.

### 2. assignRoleToUser tidak validasi user_id lintas merchant
- **Lokasi**: `apps/api/src/rbac/rbac.controller.ts:171-188` + `apps/api/src/rbac/rbac.service.ts:214-239`
- **Kategori**: cross-tenant-scope
- **Severity**: HIGH
- **Deskripsi**: `POST /rbac/user-roles` (`assignRoleToUser`) validasi `dto.outlet_id` milik merchant caller lewat `@ScopeByOutlet('body.outlet_id')` + `ScopeByOutletGuard`, tapi tidak pernah validasi `dto.user_id`. Caller dengan permission `role.assign` bisa assign role di outlet miliknya ke `user_id` milik merchant lain, merusak batas tenant di `user_roles`.
- **Rekomendasi singkat**: Di `assignRoleToUser`/`revokeRoleFromUser`, verifikasi `dto.user_id` milik merchant yang sama dengan outlet (`prisma.users.findFirst({ where: { id: dto.user_id, merchant_id } })`) sebelum create/remove assignment.

### 3. GET /rbac/roles — guard di-comment
- **Lokasi**: `apps/api/src/rbac/rbac.controller.ts:52`
- **Kategori**: guard-disabled
- **Severity**: MEDIUM
- **Deskripsi**: `@RequirePermission('role.read')` di-comment. User terautentikasi manapun (role apapun) bisa list semua role beserta full permission set-nya.
- **Rekomendasi singkat**: Uncomment decorator.

### 4. GET /rbac/permissions — guard di-comment
- **Lokasi**: `apps/api/src/rbac/rbac.controller.ts:110`
- **Kategori**: guard-disabled
- **Severity**: MEDIUM
- **Deskripsi**: `@RequirePermission('permission.read')` di-comment, user terautentikasi manapun bisa enumerate semua permission code di sistem — reconnaissance untuk privilege-escalation.
- **Rekomendasi singkat**: Uncomment decorator.

## Shifts module (`apps/api/src/shifts`)

### 5. findByOutlet tidak scope merchant_id
- **Lokasi**: `apps/api/src/shifts/shifts.controller.ts:55-67` + `apps/api/src/shifts/shifts.service.ts:134-161`
- **Kategori**: cross-tenant-scope
- **Severity**: CRITICAL
- **Deskripsi**: `GET /shifts/outlet/:outlet_id` didokumentasikan "merchant-scoped" tapi controller (baris 65) tidak pass `merchantId` ke service, dan `ShiftsService.findByOutlet(outletId)` query `prisma.shifts.findFirst({ where: { outlet_id: outletId } })` tanpa filter merchant. User terautentikasi dengan permission `shift.read` bisa supply `outlet_id` merchant lain dan dapat data shift itu — termasuk transaction list dan nama/username pemilik shift. Method lain di service file yang sama (`findOne`, `getShift`, `closeShift`, dll) sudah benar scope via `outletIds` dari `merchant_id`; handler ini yang kelewatan.
- **Rekomendasi singkat**: Tambah param `merchantId` ke `findByOutlet` dan filter `outlet_id: { in: outletIds }` (atau validasi outlet milik merchant dulu), samakan pola dengan method lain di file ini.

## Uploads module (`apps/api/src/uploads`)

### 6. Uploads tanpa merchant scoping sama sekali
- **Lokasi**: `apps/api/src/uploads/uploads.controller.ts:68-101` + `apps/api/src/uploads/uploads.service.ts:62-84` (schema: `apps/api/prisma/schema.prisma:335-351`)
- **Kategori**: cross-tenant-scope
- **Severity**: HIGH
- **Deskripsi**: Model Prisma `uploads` tidak punya kolom `merchant_id` (atau tenant apapun). `GET /uploads/:id`, `GET /uploads/:id/signed-url`, `DELETE /uploads/:id` semua resolve murni by `id` tanpa ownership check. User terautentikasi dengan permission `upload.read`/`upload.delete` (ada di sebagian besar role staff) bisa lihat metadata, generate signed URL, atau **hapus permanen** file merchant lain (product image, logo, avatar) dengan menebak/observe UUID.
- **Rekomendasi singkat**: Tambah `merchant_id` ke `uploads` (isi saat upload dari `@CurrentUser('merchant_id')`), filter ketiga method service by itu; return 404 untuk ID lintas-tenant.

### 7. setImage/setAvatar tidak validasi ownership upload
- **Lokasi**: `apps/api/src/products/products.service.ts:334-336`, `apps/api/src/merchants/merchants.service.ts:190-192`, `apps/api/src/outlets/outlets.service.ts:158-160`, `apps/api/src/users/users.service.ts:210-212`
- **Kategori**: cross-tenant-scope
- **Severity**: LOW
- **Deskripsi**: Di tiap flow `setImage`/`setAvatar`, `prisma.uploads.findUnique({ where: { id: uploadId } })` cuma validasi upload exist, tidak pernah cek milik merchant caller. Karena `uploads` tanpa scoping sama sekali (temuan #6), ini exploit path konkret buat attach upload merchant lain sebagai product/merchant/outlet/user image milik sendiri.
- **Rekomendasi singkat**: Fix scoping `uploads` (temuan #6) otomatis nutup ini juga; alternatif cek `upload.uploaded_by_id` merchant match dulu.

## Users module (`apps/api/src/users`)

### 8. GET /users tanpa permission guard
- **Lokasi**: `apps/api/src/users/users.controller.ts:50-61`
- **Kategori**: missing-auth-guard
- **Severity**: MEDIUM
- **Deskripsi**: `findAll` tidak punya `@RequirePermission()`, beda dari handler sibling lain di controller ini. `PermissionGuard.canActivate` treat metadata permission yang hilang sebagai "allow" (`permission.guard.ts:31-34`), jadi user terautentikasi manapun — termasuk role cashier — bisa list semua user merchantnya (nama, email, avatar). Bukan cross-tenant, tapi bypass RBAC gate yang seharusnya ada.
- **Rekomendasi singkat**: Tambah `@RequirePermission('user.read')`, samakan dengan route user-management lain.

## Auth / JWT (`apps/api/src/auth`)

### 9. JWT secret fallback hardcoded
- **Lokasi**: `apps/api/src/auth/strategies/jwt.strategy.ts:20-22`
- **Kategori**: secret-exposure
- **Severity**: MEDIUM
- **Deskripsi**: `secretOrKey: config.get<string>('JWT_SECRET') || 'dev_secret_change_me_in_production_2026'` — kalau `JWT_SECRET` tidak diset di deployment (misconfig, `.env` lupa), app diam-diam sign & verify token pakai fallback constant hardcoded, bukan fail-fast. Siapapun yang baca source ini bisa forge JWT valid untuk `sub` (user id) manapun terhadap deployment begini.
- **Rekomendasi singkat**: Fail fast di bootstrap kalau `JWT_SECRET` tidak diset (throw di `main.ts`/module init), jangan silent fallback ke constant.
